# sds-lite-lab

**软件定义存储（SDS）核心机制原型**：GF(256) 有限域与 **Reed-Solomon 纠删码**、
**一致性哈希环与副本放置**、**WAL + CRC 崩溃恢复**、**写时复制块存储与快照**、
LRU 缓存、多线程 IO 与基准测试。

**C++17、零第三方依赖**，一条 `make` 命令跑完全部单元测试（**164 项**）、
崩溃注入测试（**101 个注入点**）与基准。

> ⚠️ **先说清楚这是什么**
> 本项目是**个人自建的存储机制实践项目**，不是任何公司的产品代码，
> **没有在真实集群上跑过、没有做过分布式部署、没有接真实盘阵**。
> 目标是把这些机制的**正确性**用可复现的方式验证出来（尤其是崩溃一致性），
> 而不是宣称做出了一个可用的存储系统。边界见文末[「边界与已知限制」](#边界与已知限制)。

---

## 为什么做这个

分布式存储的面试与笔试，问来问去其实是几个很具体的问题：
**"任意两块盘坏了数据还在吗？""扩容时搬多少数据？""断电了会不会丢已经写成功的数据？"
"快照为什么不占空间？"** —— 这些问题每一个都能用代码算出来，而不是背概念。

| 问题 | 模块 | 实测结论 |
|---|---|---|
| 盘坏了数据还在吗 | `ec_rs.cpp` | EC(4+2) **15 种双盘失效组合全部恢复**，空间只花 1.50x（三副本 3.00x） |
| 扩容要搬多少数据 | `hash_ring.cpp` | 10 → 11 节点迁移 **7.07%**（理想 9.09%，取模哈希≈100%） |
| 断电会丢已确认的写吗 | `wal.cpp` | **101 个崩溃注入点全部通过**，已 fsync 的记录一条不丢 |
| 快照为什么不占空间 | `cow_store.cpp` | 快照只冻结映射表；空间开销只发生在"快照之后又被改写"的块上 |
| 多线程能提速吗 | 全局一致性 | **不能**：8 线程比 1 线程慢 23%，瓶颈是全局锁（见下） |

## 快速开始

```bash
make test      # 164 项单元测试
make crash     # 崩溃一致性：101 个注入点（干净掉电 + 撕裂写）
make bench     # 基准：EC 编解码 / 哈希环 / WAL / 缓存 / 并发块写
make asan      # 用 AddressSanitizer + UBSan 重跑测试
make tsan      # 用 ThreadSanitizer 重跑并发用例
```

只需要 `g++/clang++` 与 `make`；`make crash` 还需要 Python 3（只是脚本驱动）。

## 各模块做了什么、实测结果如何

> 下面所有数字都是 `make test` / `make crash` / `make bench` 的**真实输出**。

### 1. Reed-Solomon 纠删码（`gf256.cpp` + `ec_rs.cpp`）

有限域 GF(2^8)（本原多项式 0x11D，与 Linux RAID6 / Jerasure 同参数）；
编码矩阵用"单位阵 + 范德蒙德"构造，解码时取存活分片组成方阵求逆。

| 指标 | 实测 |
|---|---|
| 域公理（逆元 / 除法 / 分配律） | 20000 组随机三元组**零违反** |
| EC(4+2) 双盘失效 | **C(6,2)=15 种组合全部完整恢复** |
| EC(4+2) 单盘失效 | 6 种全部恢复 |
| 存活分片不足 k | 返回 `NotEnoughShards`，**绝不返回错数据** |
| 空间开销 | EC(4+2) **1.50x**、EC(8+3) 1.38x、EC(10+4) 1.40x（三副本 3.00x） |
| 编码吞吐 | EC(4+2) **0.32 GB/s**、EC(8+3) 0.23 GB/s、EC(10+4) 0.18 GB/s（单线程） |
| 解码吞吐 | EC(4+2) 0.23 GB/s（恢复 2 片） |

### 2. 一致性哈希与副本放置（`hash_ring.cpp`）

| 指标 | 实测 |
|---|---|
| 定位吞吐 | **3386 万次/秒（30 ns/次）** |
| 10 → 11 节点迁移比例 | **0.0707**（理想 0.0909；取模哈希接近 1.0） |
| 副本放置 | 3 副本落在 **3 个不同物理节点**（同一节点的多个虚拟节点不会占满副本位） |
| 负载偏斜 vs 虚拟节点数 | 1 个 **28.18x** → 16 个 4.64x → 128 个 2.23x → 1024 个 **1.46x** |

> **虚拟节点数的取舍**：偏斜随虚拟节点数单调改善，但内存与查找开销线性增长。
> 128 → 1024 只把偏斜从 2.23x 降到 1.46x，而环上节点数翻了 8 倍 ——
> 实际系统通常取 100~200 并在上层做负载均衡，而不是无限加大。

### 3. WAL 与崩溃恢复（`wal.cpp`）

记录格式 `[len:4][crc32:4][payload]`；重放时逐条校验 CRC，
**遇到第一条不完整/校验失败的记录就停在那里并截断**。

| 场景 | 实测 |
|---|---|
| 干净掉电（fsync 后直接 `_exit(9)`） | **1~50 条全部完整恢复，0 次修复** |
| 撕裂写（最后一条只写一半就掉电） | **已确认的 1~50 条全部完好 + 1 次尾部修复** |
| CRC 被篡改 | 只保留损坏点之前的记录，**不把脏数据当有效数据** |
| 崩溃后继续写入 | 恢复 12 条（7 条老数据 + 5 条新数据），一切正常 |
| 写入吞吐（不 fsync） | 174,555 条/秒（43.95 MB/s） |
| 写入吞吐（**带 fsync**） | **2,813 条/秒（356 µs/次）** |

> **这张表最该记住的一行是最后两行**：加不加 fsync 差了 **62 倍**。
> "数据不能丢"从来不是免费的，它是用每次写入 356 µs 的等待换来的 —— 这也是
> 为什么真实存储要在"批量提交 / 组提交"上做文章（本项目没做组提交）。

### 4. 写时复制块存储与快照（`cow_store.cpp`）

| 场景 | 实测 |
|---|---|
| 快照隔离 | 写快照后改写活动卷，**活动卷读到新数据、快照仍读到老数据** |
| 快照开销 | 创建快照不复制数据；只有"快照后又改写"的块才新增物理块 |
| 回收 | 删除快照后，不再被引用的物理块被回收（3 → 2） |
| 语义检查 | 写长度不等于块大小直接报错 —— 这是块存储的语义底线 |

### 5. 缓存与并发（`cow_store.cpp` / `hash_ring.cpp`）

| 指标 | 实测 |
|---|---|
| LRU 淘汰顺序 | 命中即提到队首，容量满时淘汰最久未用 |
| 热点负载命中率 | 容量 1024、90% 访问落在 200 个键时 **92.00%** |
| 缓存吞吐 | 767 万次/秒 |
| 线程池 | 8 线程跑完 10000 个任务 |
| 8 线程并发写 16000 个块 | 抽查全部正确（无丢失更新） |
| **4 线程并发追加 WAL 2000 条** | **成功返回 2000 条 = 重放 2000 条** |
| 并发块写吞吐 | 1 线程 **67.35 万 IOPS** → 8 线程 **51.59 万 IOPS（反而降 23%）** |

> **最后一行是本项目最想讲的一条负面结论**：并发块写不升反降，
> 原因是 COW 映射表用了一把**全局互斥锁**，线程一多就全耗在锁竞争上。
> 真实存储的数据路径必须按分片加锁 / 无锁化 / 每核一份元数据来设计 ——
> **本项目明确没有做这一步**，所以它只能作为机制原型，不能当性能参考。

## 开发过程中被测试抓出来的真问题

**下面每一条都是"看起来对、跑起来错"的**，也是这个项目最值得讲的部分：

1. **并发追加 WAL 会写坏（最严重的一条）**
   一条记录原本分**两次 `write()`**（先写头、再写数据）。4 个线程并发追加时，
   两次写会交错 —— 落盘变成"头是甲的、数据是乙的"，CRC 全部对不上。
   实测：**2000 条全部"成功返回"，重放却得到 0 条**（写入方以为成功了，数据其实是垃圾）。
   修法两条一起上：**把一条记录拼成一个缓冲、只发一次 `write()`**（`O_APPEND` 下单次写是原子的）
   ＋ **加互斥锁串行化**。修完 2000 = 2000。

2. **给 WAL 加锁时把自己锁死了两次**
   ① `open()` 持锁后又调用带锁的 `replay()` → 自死锁，测试直接卡住不返回；
   ② `reset()` 持锁后又调用 `open()` → 同样死锁。
   修法：拆出**不带锁的 `replay_locked()`**，`reset()` 直接复用已打开的 fd；
   `replay()` 是 const 方法却要加锁，所以 `mu_` 必须声明为 `mutable`。

3. **Windows 上文本模式把二进制数据当成了文本**
   CRT 默认按**文本模式**打开文件，遇到字节 `0x1A`（Ctrl-Z）当成 EOF。
   实测：写 100 条记录，**重放只恢复出 18 条**（第一条含 0x1A 的记录之后就断了）。
   修法：所有 `open()` 一律加 `O_BINARY`（POSIX 下定义为 0）。

4. **虚拟节点数与偏斜的关系，我一开始估错了**
   我以为 128 个虚拟节点能把负载偏斜压到 1.25x 以内，实测 **2.23x**。
   按理论算：单节点份额标准差 ≈ √(p(1-p)/V)，V=128、p=0.2 时约 3.5%，
   5 个节点取 max/min 之后落在 2x 附近**本来就是正常结果**，是我把门限设错了。
   现在测试改成"**随虚拟节点数单调改善**"这个真正成立的判据，并把 4 个点都量出来。

5. **`pread` 在 Windows 上的等价实现并不等价**
   POSIX 的 `pread` 是"带偏移的原子读"，Windows 没有；
   垫片用 `_lseeki64 + _read` 模拟，**会改动文件偏移**，多线程下不等价。
   所以代码里明确标注：目标平台是 Linux，Windows 垫片只服务于单线程开发测试。

6. **十六进制转义吃掉了后面的字符**
   `"\xDD" "1234"` 如果写成 `"\xDD1234"`，编译器会把 `1234` 一起当成转义序列
   （`hex escape sequence out of range`）。测试里制造"撕裂写"的数据就踩了这个。

7. **`truncate()` 在 Windows 上不存在、`ftruncate()` 才是可移植写法**
   WAL 重置原本用 `truncate(path, 0)`，在 Windows 上直接编译不过。

## 边界与已知限制

**做过的**：GF(256) 运算、Reed-Solomon 编解码与重建、一致性哈希与副本放置、
WAL + CRC + 崩溃恢复、写时复制块存储与快照、LRU 缓存、线程池、
单元测试（164 项）、崩溃注入测试（101 个注入点）、微基准。

**没做的 / 不能声称的**：

- **没有分布式**：全部是**单机单进程**。没有节点间通信、没有 RPC、
  没有一致性协议（Raft/Paxos）、没有元数据集群、没有跨节点重建、
  也没有真正的数据迁移（只**计算**了迁移比例，没有搬数据）。
- **没有接真实存储**：所有数据都在内存映射表 / 本地文件里，
  没有裸盘、没有 `O_DIRECT`、没有 NVMe/SCSI、没有 SSD 磨损与写放大、没有 RAID 卡。
- **没有 SPDK / DPDK / RDMA**：这些是 XSKY 这类公司数据路径上的关键栈，本项目**完全没碰**。
- **没有性能优化**：COW 是全局锁（实测并发反降），EC 是逐字节查表乘法（没有 SIMD），
  缓存没有分段锁，WAL 没有组提交。**本项目的数字只用于横向比较机制，不代表工程性能。**
- **快照没有持久化**：`CowBlockStore` 的映射表在内存里，进程退出即丢；
  WAL 是唯一落盘的部分，而且**只写了日志、没有写"真正的数据文件"** ——
  也就是说它验证的是**日志本身的崩溃一致性**，不是完整存储栈的端到端一致性。
- **没有做**：数据压缩、去重、分级存储、备份、克隆、精简置备、QoS、
  监控指标暴露、故障注入以外的稳定性测试（长稳、掉盘、慢盘）。
